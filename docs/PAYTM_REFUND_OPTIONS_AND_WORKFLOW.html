Payment Debited, Order Not Placed: Refund Options

How Paytm Documentation defines refunds and how V Foods executes them seamlessly

The Real-World Situation

In a fast-moving cafeteria, a customer enters their UPI PIN and their bank account is debited ₹120. However, the order is NOT placed (e.g. phone lost internet right after UPI authorization, customer closed the app, or the 10-minute checkout timer expired while paying).

1. Paytm Gateway State:
Transaction is marked TXN_SUCCESS. Funds reside securely at Paytm.
≠
2. V Foods Order State:
Order status remains awaiting_payment or cancelled. No food token issued.

Official Refund Options Provided in Paytm Documentation

⚡
Option A: Automated Server-to-Server Refund API

Documented by Paytm as the programmatic reversal channel:

  • Endpoint: POST https://securegw.paytm.in/refund/apply
  • How it works: The merchant server sends a signed JSON request with Merchant ID, Transaction ID, and a unique Refund ID.
  • Paytm Action: Paytm automatically reverses the funds to the customer's source account (UPI / Bank / Card).
  • V Foods Usage: Primary method used for automated and one-click refunds.
🖥️
Option B: Paytm Merchant Dashboard (Manual Portal)

Documented by Paytm as the administrative backup channel:

  • Portal: https://dashboard.paytm.com
  • How it works: Merchant logs into the Paytm web portal, searches the Order ID / Transaction ID, and clicks "Initiate Refund".
  • Paytm Action: Paytm processes the refund from the web interface.
  • V Foods Usage: Super Admin emergency backup. (Store managers do not need this because V Foods automates it via Option A).

How V Foods Triggers the Paytm Refund API

The three real-world execution paths that protect customer money
🤖
Trigger 1: Automatic Background Reconciler

When: The customer walked away or closed their browser without returning to V Foods.

  • A background task (/admin/payments/reconcile) scans for stuck payments older than 2 minutes.
  • It queries Paytm’s Transaction Status API. If Paytm confirms payment was taken but the 10-minute order timer expired, it automatically initiates the refund.
  • Human effort required: ZERO.
📱
Trigger 2: Customer Taps "Check Status" in App

When: The student is looking at their phone and sees their screen stuck on "Payment Pending".

  • Customer taps "Check Payment Status".
  • Backend queries Paytm live. If payment succeeded but order window expired, the backend initiates the refund on the spot.
  • Student's screen instantly displays: "100% Refund Initiated (Ref: refund-482)".
🏪
Trigger 3: Store Manager One-Click Refund

When: Student shows their bank SMS at the counter saying money was debited without a token.

  • Manager opens the "Payments Needing Attention" screen (/admin/payments/attention).
  • Manager sees the transaction with order unplaced.
  • Manager taps "Cancel & Refund". Backend calls Paytm Refund API immediately.

Where Does the Money Go & Settlement Speed?

Customer Payment Source Where the Money Returns Turnaround Time
UPI (GPay / PhonePe / Paytm) Directly credited back to the customer's original linked bank account via NPCI. Instant to a few hours
V Foods In-App Wallet Directly re-credited to the customer's in-app wallet balance. Instant (0 seconds)
Debit / Credit Card Credited back to the card account through the card network (Visa / Mastercard / RuPay). 1 to 3 banking days
Netbanking Credited back to customer's savings account via bank IMPS/NEFT reversal. 2 to 4 banking hours

Behind the Scenes: The V Foods Python Backend Function

In backend/main.py, line 459, the backend executes:
async def _paytm_initiate_refund(payment_id, amount, reason, order_id):

  • Generates a deterministic reference: refId = f"refund-{payment_id}".
  • Calculates HMAC-SHA256 signature using the secret merchant key.
  • Transmits HTTP POST to https://securegw.paytm.in/refund/apply.
  • Updates the PostgreSQL refunds table to record the gateway refund ID.

Safety Guarantees & Executive Summary

How duplicate refunds are prevented and why this architecture guarantees zero financial loss

What Prevents Duplicate / Double Refunds?

A common concern is: "What if the student taps 'Check Status' 5 times, or both the automated system and the store manager click Refund?"

1. Deterministic Key:
V Foods generates: refId = refund-<payment_id>. There is only one valid refund key per payment ID.
2. Database Constraint:
In PostgreSQL, refunds.refund_ref is marked UNIQUE. Inserting a duplicate key raises a constraint error.
3. Paytm Gateway Lock:
Paytm uses refId as an idempotency key. If Paytm sees the same refId again, it returns the existing status without debiting the merchant twice.
